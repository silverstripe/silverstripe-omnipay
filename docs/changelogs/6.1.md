# 6.1.0

If your database contains payments made with omnipay 5.x or older, read the [upgrading guide](../en/Upgrading.md).

## Payment message migration

Fixes [#123](https://github.com/silverstripe/silverstripe-omnipay/issues/123) and
[#183](https://github.com/silverstripe/silverstripe-omnipay/issues/183).

6.0 replaced the 41 class-per-type payment message classes with a single `PaymentMessage` with a `Type` column, but
its upgrade path lost data. 6.1 adds a complete migration:

- New `SilverStripe\Omnipay\Migration\PaymentMessageMigrator`, which runs automatically on `db:build`. It copies
  `Gateway`, `Reference`, `Code`, `SuccessURL` and `FailureURL` from the legacy `Omnipay_GatewayMessage` and
  `Omnipay_GatewayRequestMessage` tables, sets `Type` from legacy class names (5.x and 3.x), and renames the legacy
  tables to `_obsolete_*`. It only fills empty values and is safe to run repeatedly. Sites that already upgraded to
  6.0 get their missing data backfilled.
- `MigratePaymentMessageTypesTask` uses the migrator and supports `--dry-run`.
- New config `PaymentMessage.migrate_legacy_messages_on_build` (default `true`).

## Deprecations

- `PaymentMessage::classForMessageType()`: it always returns `PaymentMessage::class`. Use `PaymentMessage::create()`.

## Bug fixes

- `_config/legacy.yml` now targets `SilverStripe\Dev\Command\DbBuild`. The 6.0 config targeted `DatabaseAdmin`,
  which doesn't exist in Silverstripe CMS 6, so it had no effect. Legacy message class names are no longer remapped
  there, because the migrator handles them.
- `MigratePaymentMessageTypesTask` and `CleanupAbandonedPaymentsTask` now register under their intended command
  names (`tasks:MigratePaymentMessageTypesTask`, `tasks:CleanupAbandonedPaymentsTask`). They previously used the
  Silverstripe CMS 5 `$segment` config, which is ignored in 6.
